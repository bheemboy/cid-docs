# <mark>Data Flow & Privacy</mark>

This page describes what data flows between a CID device and the CID Hub, what does **not** flow, where the Hub stores it, and how long it is retained. It is the canonical answer for IT-review questions on data transit, telemetry inventory, residency, and privacy stance.

## What flows between the CID and the CID Hub

The CID exchanges only **operational metadata, configuration, and credentials** with the CID Hub. **Customer laboratory data never traverses the Hub.**

- **No PHI (Protected Health Information)** is transmitted between the CID and the Hub.
- **No PII** is transmitted beyond the names and email addresses of the internal users a customer chooses to invite to administer their tenant. Those identifiers are stored in **AWS Cognito on the Hub side**; they are not stored on the CID device itself.
- **No laboratory data, sample data, chromatograms, or analytical results** are transmitted to the Hub. Those remain on the customer's local network and are handled by [OpenLab CDS](https://www.agilent.com/en/product/software-informatics/analytical-software-suite/chromatography-data-systems/openlab-cds).
- All traffic between the CID and the Hub is **encrypted in transit** using TLS (HTTPS for REST/file transfer; MQTT over TLS for the IoT control plane).

## Data Types Summary

The nine categories below are the authoritative inventory of what crosses the CID ⇄ Hub boundary.

| Data Category | Direction | Contains Sensitive Data | Transport | Customer Visible |
|---|---|---|---|---|
| Device Registration | CID → Hub | No | HTTPS / TLS | Yes (Portal) |
| IoT Credentials | Hub → CID | Yes (X.509 certificates) | HTTPS / TLS | No |
| Agent-Reported State | CID → Hub | No | MQTT / TLS (IoT shadow) | Yes (Portal) |
| Hub Commands | Hub → CID | Sometimes (configuration data) | MQTT / TLS | Yes (Portal) |
| Software Downloads | Hub → CID | No | HTTPS / TLS | Yes (Portal) |
| Password Updates | Hub → CID | Yes (rotated credentials) | MQTT / TLS | No |
| Activity Logs | CID → Hub | No | HTTPS / TLS | Yes (Portal) |
| Configuration Data | Bidirectional | Partial (IP addresses, hostnames) | HTTPS or MQTT / TLS | Yes (Portal) |
| User Actions | Portal → Hub | No | HTTPS / TLS | Yes (Portal) |

### Telemetry inventory by direction

**CID → Hub.** Device identity and operational state: CID name, hardware platform identifier, MAC address, House-NIC IP / FQDN, software-version selections, registration status, slot information for the agent and Windows VM, and agent-reported shadow state (capped at 6000 characters by the IoT shadow). The AIC Instrument-NIC connection metadata is intentionally hidden from the Hub view — only customer-friendly identifiers are surfaced.

**Hub → CID.** IoT X.509 client certificates issued at registration, signed software-update manifests, rotated administrative credentials (Cockpit / Windows console passwords), and configuration commands (for example, allow-list updates, time-zone changes, software-version pinning).

**Portal → Hub.** User authentication (AWS Cognito), tenant administration actions (invite user, change role, approve a remote-access request), and audit-trail entries generated by those actions.

### Region and residency

All production CID ⇄ Hub traffic lands in **AWS `us-east-1`**. This includes the Registration API, the Management API, AWS IoT Core (`a3cb4mwmdz2oep-ats.iot.us-east-1.amazonaws.com`), AWS IoT Secure Tunneling, Cognito, the PostgreSQL data store, and the production image bucket. Image delivery is fronted by **Amazon CloudFront** (`files.cid.agilent.com`); the origin remains `us-east-1`. The one current exception in the broader connectivity footprint is the **Linux package mirror** in `us-west-2` (`agilent-aws-sbx-51-yum-rpm-repo.s3.us-west-2.amazonaws.com`), which is consulted only for OS-package retrieval and does not carry any of the nine data categories above.

See [Internet Requirements](../reference/system-requirements#internet-requirements) for the corresponding firewall allow-list.

### Retention

- **CID Hub activity and audit logs** (the "Activity Logs" row and the audit trail of "User Actions" / "Hub Commands") are kept in online storage for **at least 7 years**.
- **IoT shadow reported state** ("Agent-Reported State") is a *latest-state* model rather than a history log — only the most recent reported document is retained per device, and is capped at 6000 characters.
- **Device registration records** ("Device Registration", "IoT Credentials", "Configuration Data") persist for the life of the CID's enrollment in the tenant; they are removed when the CID is deactivated.
- **Software-download artifacts** are immutable, version-tagged objects in the production image bucket; the CID retains only the version currently installed and the prior version available for rollback.

For the audit-trail surface, capture cadence, and review workflow, see [Audit & Compliance](./audit-and-compliance) and [View Activity Logs](../howto/monitoring/view-activity-logs).

## What does **not** transit the Hub

The following stay entirely on the customer's local network and are handled by OpenLab CDS, not by the CID Hub:

- Chromatograms, mass spectra, UV/DAD spectra, and all other instrument acquisition data.
- Sample sequences, methods, processed results, and reports.
- Electronic records and signatures governed by 21 CFR Part 11 / EU GMP Annex 11 (these are CDS responsibilities; deploying CDS on a CID does not change the documented CDS Part 11 posture).
- LIMS / ELN integration traffic between CDS and the customer's informatics systems.
