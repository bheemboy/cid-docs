# <mark>Data flow and privacy</mark>

This page describes what data flows between a CID device and the CID Hub, what does not flow, where the Hub stores it, and how long it is retained. Use it to answer IT-review questions on data transit, telemetry inventory, residency, and privacy.

## What flows between the CID and the CID Hub

The CID exchanges only **operational metadata, configuration, and credentials** with the CID Hub. **Your laboratory data never traverses the Hub.**

- **No PHI (Protected Health Information)** is transmitted between the CID and the Hub.
- **No PII** is transmitted beyond the names and email addresses of the users you choose to invite to administer your tenant. Those identifiers are stored in AWS Cognito on the Hub side; they are not stored on the CID device itself.
- **No laboratory data, sample data, chromatograms, or analytical results** are transmitted to the Hub. Those remain on your local network and are handled by [OpenLab CDS](https://www.agilent.com/en/product/software-informatics/analytical-software-suite/chromatography-data-systems/openlab-cds).
- All traffic between the CID and the Hub is **encrypted in transit** using TLS (HTTPS for REST/file transfer; MQTT over TLS for the IoT control plane).

## Data types summary

The nine categories below are the authoritative inventory of what crosses the CID–Hub boundary.

| Data category | Direction | Contains sensitive data | Transport | Customer visible |
|---|---|---|---|---|
| Device Registration | CID → Hub | No | HTTPS / TLS | Yes (Portal) |
| IoT Credentials | Hub → CID | Yes (X.509 certificates) | HTTPS / TLS | No |
| Agent-Reported State | CID → Hub | No | MQTT / TLS (IoT shadow) | Yes (Portal) |
| Hub Commands | Hub → CID | Sometimes (configuration data) | MQTT / TLS | Yes (Portal) |
| Software Downloads | Hub → CID | No | HTTPS / TLS | Yes (Portal) |
| Password Updates | Hub → CID | Yes (rotated credentials) | MQTT / TLS | No |
| Activity Logs | CID → Hub | No | HTTPS / TLS | Yes (Portal) |
| Configuration Data | Bidirectional | Partial (IP addresses, hostnames) | HTTPS or MQTT / TLS | Yes (Portal) |
| User Actions | Portal → Hub | No | HTTPS / TLS | Yes (Portal) |

### Telemetry inventory by direction

The following summarizes what each side of the connection sends.

**CID → Hub.** Device identity and operational state: CID name, hardware platform identifier, MAC address, House-NIC IP / FQDN, software-version selections, registration status, slot information for the agent and Windows VM, and agent-reported shadow state. Only customer-friendly identifiers are surfaced; low-level instrument-network metadata is not sent to the Hub.

**Hub → CID.** IoT X.509 client certificates issued at registration, signed software-update manifests, rotated administrative console credentials, and configuration commands (for example, allow-list updates, time-zone changes, software-version pinning).

**Portal → Hub.** User authentication (AWS Cognito), tenant administration actions (invite user, change role, approve a remote-access request), and audit-trail entries generated by those actions.

### Field-level telemetry inventory

The fields below are the complete set the CID agent reports to the Hub. Every field travels CID to Hub only. Most are operational identifiers classified Low; the fields touching network or service-account identity are classified Medium.

| `identity` / `platform` | Host OS type (for example, oracle-linux) | Low |
| `acImageVersion` / `acImageId` | CID agent image version | Low (operational) |
| `aicImageVersion` / `aicImageId` | Windows VM (AIC) image version | Low (operational) |
| `driverIds` | Installed CDS instrument driver versions | Low (operational) |
| `windowsUpdateIds` | Applied Windows updates | Low (operational) |
| `ac_client.version` | Agent client version | Low |
| `ac_update.version` | Update utility version | Low |
| `instruments_info[]` | Connected instrument metadata (model, serial, status); no sample or analytical data | Low |
| `network_cards` | Linux host NIC configuration (IP, VLAN) | Medium (infrastructure) |
| `aic_network_cards` | Windows VM NIC configuration (IP, VLAN) | Medium (infrastructure) |
| `agent` | Daemon status, uptime | Low |
| `cid_connectivity` | Connectivity status, last check, type | Low |
| `aic.olss_server_fqdn` | OpenLab server hostname | Medium (infrastructure) |
| `aic.olss_connection_type` | Connection type to OpenLab Server | Low |
| `aic.olss_username` | OpenLab service-account username | Medium (internal-user identifier) |
| `command` | Command name, status, progress, parameters | Low (operational) |
| `name` (thing name) | Device hostname | Low |
| `windows_vm` | VM state, uptime | Low |
| `certificate_authorities` | Trusted CA list, sync status | Low |
| `downloads[]` | Download progress (presigned URL stripped before send) | Low |

| `reported_date` | ISO 8601 timestamp of the report | Low |
| `version` | Incrementing state-version number | Low |

**Sanitized before transmission or storage.** Credentials and private keys are removed at the agent or stripped before the Hub stores anything: the Linux admin and `agilentac` passwords, the AC and AIC SSH private keys, the OpenLab Server password (`aic.olss_password`), the technician token (`aic.tech_token`), and the presigned download URLs. None of these leave the device or are persisted on the Hub.

### Region and residency

All production CID–Hub traffic lands in **AWS `us-east-1`**. This includes the Registration API, the Management API, AWS IoT Core, AWS IoT Secure Tunneling, Cognito, and content delivery. Image delivery is fronted by **Amazon CloudFront** (`files.cid.agilent.com`); the origin remains `us-east-1`.

See [Internet requirements](../reference/system-requirements#internet-requirements) for the corresponding firewall allow-list.

### Retention

- **Activity and audit logs** (the Activity Logs row and the audit trail of User Actions / Hub Commands) are retained online for at least 7 years. There is no user-accessible export path to a customer SIEM at this time.
- **Agent-reported state.** The AWS IoT device shadow holds only the latest reported document per device. On the Hub side the reported state is also persisted to the database in two forms: a most-recent snapshot that is overwritten on each update, and a versioned history that keeps prior reported-state versions for the life of the device's enrollment.
- **Device registration records** (Device Registration, IoT Credentials, Configuration Data) persist for the life of the CID's enrollment in the tenant.
- **Removal is by device deletion, not by an automatic purge window.** No scheduled purge runs on reported-state history or activity logs. When a CID is removed from the tenant, its registration record, reported-state history, and activity-log entries are deleted together.
- **Software-download artifacts** are immutable, version-tagged objects; the CID retains only the version currently installed and the prior version available for rollback.

For the audit-trail surface, capture cadence, and review workflow, see [Audit and compliance](./audit-and-compliance) and [View Activity Logs](../howto/monitoring/view-activity-logs).

## What does not transit the Hub

The following stay entirely on your local network and are handled by OpenLab CDS, not by the CID Hub:

- Chromatograms, mass spectra, UV/DAD spectra, and all other instrument acquisition data.
- Sample sequences, methods, processed results, and reports.
- Electronic records and signatures governed by 21 CFR Part 11 / EU GMP Annex 11 (these are CDS responsibilities; deploying CDS on a CID does not change the documented CDS Part 11 posture).
- LIMS / ELN integration traffic between CDS and your informatics systems.
